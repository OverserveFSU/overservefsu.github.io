Abstract

LLM agents automate business workflows by calling tools and deciding when the task is complete. In SaaS deployments that bundle internal execution into an outer request, additional model and tool calls consume provider resources. OverServe is a multi-agent framework for constructing resource-amplification attacks through tool–prompt co-design. It pairs an MCP status tool with a completion-confirmation prompt. Each tool call returns accurate status and terminates normally, while an unfinished service condition can sustain repeated checking after the original business task is done.

The framework constructs service-specific pairs, reviews their components, and evaluates victim executions. The manuscript reports selected tasks across four victim models and nine core benchmarks, plus a command-line extension. This page presents the framework, reported call-overhead results, controlled interaction experiments, and a separate native-service candidate that remains to be evaluated.

Threat Model

The attacker submits a third-party MCP tool and a completion prompt. The provider retains control of the victim agent, existing tools, service backend, permissions, and task verification. The manuscript studies a truthful status tool under controlled synchronization conditions: when updates continue, the service condition can remain pending even after the original task is completed.

Method

OverServe uses service descriptions, the available tool inventory, and the original task to construct a status tool and matching completion prompt. It then combines component reviews with victim-execution feedback, selects fixed pairs, and evaluates independent replays.

Figure 2. The author’s original framework figure: candidate construction and review, matched victim runs, and selection with independent confirmation.

Pair construction

A writer proposes service-specific tool implementations and completion prompts from candidate completion conditions.

Component review

Reviewers assess source code, runtime completion behavior, and prompt benignness under the declared protocol.

Victim evaluation

Execution records include calls, original-task checks, and stopping reasons. Selected pairs are frozen before independent replay.

Example: A Native-Service Dependency Cycle

The following candidate separates two conditions between the prompt and the tool. The prompt maintains a reference to the latest announcement; the tool checks whether that announcement quotes the current description. It uses existing service APIs and permissions, without adding an update producer or simulated pending state.

02 / PROPOSED STATUS TOOLRead-only · illustrative core
announcement_status(team_id, channel_id)

Reads the channel and latest announcement. Reports whether the announcement quotes the current, nonempty channel description. It does not modify either record.

def announcement_status(team_id, channel_id):
    view = read_native_view(team_id, channel_id)
    if not view["read_complete"]:
        return {"status": "unknown", "complete": None}

    description = view["description"] or ""
    latest = view["latest_message"]
    ready = (
        latest is not None
        and bool(description.strip())
        and description in latest["plain_text"]
    )
    return {"complete": ready}
✓ Checks actual content; the tool imposes no LATEST-ID rule.
